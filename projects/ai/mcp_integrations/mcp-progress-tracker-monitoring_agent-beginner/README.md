# MCP Progress Tracker: Monitoring Agent

**Domain:** ai | **Subdomain:** mcp_integrations | **Difficulty:** beginner | **Est. build time:** 2-4 hours

---

## Overview

MCP Progress Tracker built as a Monitoring agent. Long tool calls report progress so clients can show spinners instead of hanging: servers send progress notifications with completed and total counts, and clients aggregate across parallel calls. Cancellation tokens let users abort stuck operations. The tracker simulates seeded long calls and aggregates progress streams. Samples synthetic topic metrics for N cycles, evaluates each reading against thresholds, prints readings and alerts.

**Core concept — MCP Progress Tracker:** Long tool calls report progress so clients can show spinners instead of hanging: servers send progress notifications with completed and total counts, and clients aggregate across parallel calls. Cancellation tokens let users abort stuck operations. The tracker simulates seeded long calls and aggregates progress streams.

**Why this matters in the real world:** File-operation tools report progress during long transfers.

---

## Features

- **Monitor**: Samples metrics, evaluates thresholds, and collects alerts.
- `read_metrics` (`read_metrics(rng, cycle)`): Sample one synthetic topic metric reading.
- `check_thresholds` (`check_thresholds(reading, thresholds)`): Return a list of alert strings for readings over threshold.
- `Monitor.run` (`Monitor.run(self, cycles, interval)`): Sample `cycles` readings, print them, return alert count.
- `main` (`main()`): Parse args and run the monitor.

## How It Works

The project is built around Periodic sampling with static threshold evaluation. Input data flows from src/main.py through the processing modules, and the overall approach runs in O(cycles) total; O(1) per sample. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the high-level design and [docs/DESIGN.md](docs/DESIGN.md) for the detailed module breakdown.
