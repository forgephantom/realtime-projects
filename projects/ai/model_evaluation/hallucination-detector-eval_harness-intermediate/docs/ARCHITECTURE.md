# Architecture (HLD) — Hallucination Detection Simulator: Eval_Harness

## Problem & Users

Hallucination Detection Simulator built as a eval_harness. Hallucinations are plausible statements that are unsupported or false. Detection strategies include checking claims against retrieved context, measuring self-consistency across multiple sampled answers, and scoring entity-level factuality. The simulation plants unsupported claims in generated text and measures detector precision and recall at claim granularity. An evaluation harness that runs test cases against a stub model, measures accuracy and latency, and adds an LLM-as-judge rubric score per case.

The intended user is a student or engineer working in ai (model_evaluation) who needs a working, runnable reference for Hallucination Detection Simulator — something they can read end to end, run in seconds, and adapt to their own data or experiments.

## Data Flow

```
test cases -> run_case (stub model + latency + exact match) -> results
results + rubric -> judge_score per case -> judged scores
results + judged -> summarize -> accuracy, latency, judge averages
```

## Storage

No persistence: cases, results, and summaries are regenerated from the seed each run.

## Scaling & Limits

Sequential runs suit hundreds of cases; thousands would want parallel workers and a persistent results store.

## Trade-offs

Exact-match correctness is strict and reproducible but penalizes correct answers phrased differently; the judge score softens that.

## Failure Handling

A stub model crash is caught per case and recorded as incorrect with the error text, so one bad case never kills the run.
