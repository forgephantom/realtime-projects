# Architecture (HLD) — LTV to CAC Ratio Dashboard: Financial_Model

## Problem & Users

LTV to CAC Ratio Dashboard built as a financial_model. The LTV to CAC ratio asks whether a customer is worth several times what it cost to acquire them. Around three is the rule of thumb: lower suggests overspending on acquisition or weak monetization, much higher can mean under-investing in growth. The ratio only means something when both halves are measured on the same cohorts. A financial modeler computing NPV, IRR by bisection, DCF valuation, break-even point, and a loan amortization schedule from seeded synthetic inputs.

The intended user is a student or engineer working in business_analyst (kpi_dashboards) who needs a working, runnable reference for LTV to CAC Ratio Dashboard — something they can read end to end, run in seconds, and adapt to their own data or experiments.

## Data Flow

```
seeded inputs -> cashflows, loan terms, unit economics
cashflows -> npv(rate) -> present value
cashflows -> irr (bisection) -> discount rate where NPV=0
cashflows -> dcf_value -> enterprise value with terminal value
unit economics -> breakeven -> units to cover fixed costs
loan terms -> amortization_schedule -> monthly payment table
```

## Storage

No persistence: inputs and schedules are regenerated from the seed each run.

## Scaling & Limits

Closed-form math suits any horizon; portfolio-scale use would vectorize across many projects.

## Trade-offs

Deterministic formulas are auditable but ignore taxes, inflation, and risk beyond the discount rate.

## Failure Handling

IRR raises a clear error when NPV has no sign change in the search range instead of returning a bogus rate.
