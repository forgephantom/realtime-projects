# Architecture (HLD) — Sliding Window Flow Control: Simulation (Logistic Growth)

## Problem & Users

Sliding Window Flow Control built as a Simulation (logistic growth). Flow control keeps fast senders from overwhelming slow receivers: the receiver advertises a window, the sender keeps unacknowledged bytes within it, and the window slides as ACKs arrive. The demo shows throughput as a function of window vs bandwidth-delay product. It is the mechanism behind TCP's self-clocking. Euler-integrates logistic growth dP/dt = r*P*(1-P/K) and prints the trajectory table with summary statistics.

The intended user is a student or engineer working in computer_science (computer_networks) who needs a working, runnable reference for Sliding Window Flow Control — something they can read end to end, run in seconds, and adapt to their own data or experiments.

## Data Flow

```
PARAMS (r, K, P0) + --steps/--dt -> simulate (Euler loop)
trajectory rows -> print_trajectory (sampled table)
rows -> start/end/peak summary
```

## Storage

In-memory only: the trajectory list exists for the run and is not persisted.

## Scaling & Limits

The trajectory is a plain list, so millions of steps would use noticeable memory; streaming or downsampling would fix that.

## Trade-offs

Explicit Euler is the simplest integrator to read and verify, at the cost of accuracy versus higher-order methods for stiff dynamics.

## Failure Handling

A non-positive carrying capacity K would flip the growth sign; the template documents K as positive and the default params keep it well-behaved.
