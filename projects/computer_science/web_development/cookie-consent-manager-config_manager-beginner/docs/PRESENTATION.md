# Presentation Guide — Cookie Consent Manager: Config Manager

## 60-Second Pitch

I built a Cookie Consent Manager that merges defaults, files, environment, and CLI flags into one validated configuration with full provenance. Privacy law requires consent before tracking: the manager shows a banner, records granular choices (necessary, analytics, marketing), blocks non-essential scripts until consent, and stores proof of consent per user.

Cookie Consent Manager in two sentences: Privacy law requires consent before tracking: the manager shows a banner, records granular choices (necessary, analytics, marketing), blocks non-essential scripts until consent, and stores proof of consent per user. Consent must be revocable and re-prompted on policy change. The audit trail is the legal artifact.

## Architecture Talking Points

- Components: `Config` plus the CLI entrypoint — each maps to a real module in `src/`, and the data-flow diagram shows how they connect.
- Algorithm: Layered merge: defaults < ini string < environment < CLI, with typed coercion; runs in O(k) over k config keys.
- Honest scaling limit: Flat key/value schema suits service config; deeply nested configs would want a tree model instead.

Use these when someone asks "how does it work?" — start with the problem, then walk the data flow, then name one trade-off. Trade-offs are what interviewers remember.

## Interview Q&A

**Q:** What is the precedence order?

**A:** Later layers win: defaults, then the INI snippet, then PREFIX_* environment variables, then --set overrides.

**Q:** How do you know where a value came from?

**A:** Every set records its layer in _sources, so the demo prints exactly where each value came from.

**Q:** How are booleans parsed?

**A:** Booleans accept true/false/1/0/yes/no/on/off case-insensitively; anything else raises ValueError.
