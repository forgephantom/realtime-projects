# Presentation Guide — Structured Request Logging: Monitoring Agent

## 60-Second Pitch

A Structured Request Logging monitoring agent in pure Python that samples synthetic metrics on a cadence, checks them against thresholds, and reports every breach. Plain-text access logs are painful to query, so structured logging emits each request as a JSON record: method, path, status, duration, user, request id, and sizes.

Structured Request Logging in two sentences: Plain-text access logs are painful to query, so structured logging emits each request as a JSON record: method, path, status, duration, user, request id, and sizes. Consistent field names let log pipelines aggregate p99 latency or error rates without regex. The middleware must also redact sensitive fields before the record leaves the process.

## Architecture Talking Points

- Components: `Monitor` plus the CLI entrypoint — each maps to a real module in `src/`, and the data-flow diagram shows how they connect.
- Algorithm: Periodic sampling with static threshold evaluation; runs in O(cycles) total; O(1) per sample.
- Honest scaling limit: Single-process in-memory sampling; real fleet monitoring would need persistence, alerting integrations, and horizontal collectors.

Use these when someone asks "how does it work?" — start with the problem, then walk the data flow, then name one trade-off. Trade-offs are what interviewers remember.

## Interview Q&A

**Q:** Where do thresholds come from?

**A:** From PARAMS thresholds, overridable per template instance; defaults are 85% CPU, 90% memory, 500ms latency.

**Q:** Are the readings reproducible?

**A:** The RNG is seeded, so the same seed replays the same readings and alerts for debugging.

**Q:** Could it run persistently?

**A:** Yes, but it would be single-process and in-memory, so it fits demos and prototypes rather than fleet monitoring.
