# Architecture (HLD) — WebSocket Backpressure Controller: Simulation (Logistic Growth)

## Problem & Users

WebSocket Backpressure Controller built as a Simulation (logistic growth). Fast producers overwhelm slow consumers: the backpressure controller monitors per-connection send buffers, applies pause/resume signals or drops to best-effort for stale data, and sheds load by disconnecting the slowest consumers first. High/low watermarks prevent oscillation. Without it, one slow client can OOM the server. Euler-integrates logistic growth dP/dt = r*P*(1-P/K) and prints the trajectory table with summary statistics.

The intended user is a student or engineer working in computer_science (web_development) who needs a working, runnable reference for WebSocket Backpressure Controller — something they can read end to end, run in seconds, and adapt to their own data or experiments.

## Data Flow

```
PARAMS (r, K, P0) + --steps/--dt -> simulate (Euler loop)
trajectory rows -> print_trajectory (sampled table)
rows -> start/end/peak summary
```

## Storage

In-memory only: the trajectory list exists for the run and is not persisted.

## Scaling & Limits

The trajectory is a plain list, so millions of steps would use noticeable memory; streaming or downsampling would fix that.

## Trade-offs

Explicit Euler is the simplest integrator to read and verify, at the cost of accuracy versus higher-order methods for stiff dynamics.

## Failure Handling

A non-positive carrying capacity K would flip the growth sign; the template documents K as positive and the default params keep it well-behaved.
